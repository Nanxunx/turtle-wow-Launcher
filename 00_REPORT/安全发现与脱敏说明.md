# 安全发现与脱敏说明

## 1. Stronghold vault 固定解锁字面量

Active 前端源码的认证实现向 Tauri Stronghold `load()` 传入固定字面量，用于打开生产环境 `vault.hold` / `AuthClient` 保存的登录 token。该值具有凭据性质，因此本交付包中的 recovered source、bundle、source map 和证据文本均不提供其原始值，统一以 `[REDACTED_APP_VAULT_KEY]` 代替。

这不影响还原认证流程、API contract、账户 key 规则或 Stronghold 数据流。

## 2. StormLib / MPQ weak signing 私钥

原始 EXE `.rdata` 在约 `0x19A0630` 出现一个完整 PKCS#8 PEM private-key 常量，其后紧邻一组 MPQ 验签公钥。官方 StormLib `src/SFileVerify.cpp` 将这一私钥命名为 `szBlizzardWeakPrivateKey`，并在 `SSignFileFinish` 中将其用于 weak MPQ signature：对 archive 计算 MD5 后使用 512-bit RSA PKCS#1 v1.5 签名。

因此可确定：

- 它来源于静态链接的 StormLib，而不是 Turtle WoW 登录认证。
- 它不是当前 Launcher EXE 的 Authenticode 签名私钥。
- 该历史 weak key 已存在于 StormLib 官方公开源码，但本交付仍不复制或复述 PEM 私钥正文。
- 原始 EXE 中该位置和存在性保留在报告中，以满足取证完整性；导出包只给出安全描述。

参考上游：`ladislav-zezula/StormLib`, `src/SFileVerify.cpp`（`szBlizzardWeakPrivateKey`, `SSignFileFinish`）。

## 3. 另一个 RSA private-key 格式标记

原样本约 `0x19F5898` 还出现 `BEGIN RSA PRIVATE KEY` 格式文本，但其静态上下文属于 libssh2/PEM parser 一类错误/格式字符串，未观察到一段紧随其后的实际 RSA PEM private-key body。因此报告仅记录“格式标记存在”，不把它误报为第二个实际 key。

## 4. Authenticode

最终 byte-level 复核确认 PE Optional Header 的 Security Directory 为 `0x1F71C00` / `0x26E8`，当前原始上传样本大小正好是该 offset 加 9,960-byte 证书表，因此完整 `WIN_CERTIFICATE` 存在。PKCS#7 叶子代码签名证书为 `O=Turtle WoW, CN=Turtle WoW`，Issuer `Sectigo Public Code Signing CA EV R36`；独立重算 Authenticode SHA-256 与 SignedData 内 digest 一致。StormLib MPQ weak-signing key 仍与 Windows Authenticode 完全是两套不同用途的密码材料。详见 `10_NATIVE_ULTIMATE/AUTHENTICODE_FORENSICS.md`。

## 5. 构建身份脱敏

Compiler/cargo path 中泄漏的构建机器用户名只作局部掩码（例如 `DRD****`），依赖版本、crate/git checkout 路径和技术证据仍保留。
